# Antora Site Structure & Conventions

The `nmecar` documentation site is generated by **Antora 3.1** from a single content component (`nmecar`) with one ROOT module. Everything contributors need to know about page placement, navigation assembly, AsciiDoc attributes, versioning, and partial reuse is defined by a small set of fixed entry points: the playbook, the component descriptor, and the `nav.adoc` / partial chain. This page documents those entry points and the conventions that keep the generated site coherent across feature-level releases.

## Single-component layout

The repository is a single Antora content source. `antora-playbook.yml` declares one source — the repository root at `HEAD`, with `start_path: docs` — so the whole site is produced from one component version rather than a multi-repo aggregation.

```yaml
content:
  sources:
    - url: .
      branches:
        - HEAD
      start_path: docs
```

The component descriptor `docs/antora.yml` fixes the component identity and points the nav at the ROOT module's `nav.adoc`:

```yaml
name: nmecar
title: nmecar
version: '2.0'
display_version: '2.0'
start_page: ROOT:index.adoc
nav:
  - modules/ROOT/nav.adoc
```

Content lives under the standard ROOT-module folders:

- `docs/modules/ROOT/pages/**` — documentation pages, organized into section subdirectories (`admin/`, `booking/`, `fleet/`, `reporting/`, `technical/`, `release-notes/`).
- `docs/modules/ROOT/partials/**` — reusable AsciiDoc fragments (nav partials, `caution.adoc`, `sonarqube.adoc`, `sonarqube_badge.adoc`).
- `docs/modules/ROOT/images/` — screenshots and static diagrams.
- `docs/modules/ROOT/examples/` — code samples included via `include::example$...[]`.

The UI bundle is vendored at `vendor/antora-ui-default.zip` so builds do not download it remotely; supplemental UI overrides live in `supplemental-ui/`, and the Sass theme source at `theme/site.scss` must be compiled to CSS before packaging (see [Build & Preview](../operations/build-and-preview.md)).

## Playbook configuration

`antora-playbook.yml` defines site-level identity, UI, AsciiDoc attributes, and extensions:

- **Site identity** — title `nmecar Documentation`, URL `http://carrental-docs.nmlabs.gr`, start page `nmecar::index.adoc`, `robots: allow`. HTML URLs use the `indexify` extension style (`urls.html_extension_style: indexify`).
- **UI** — vendored bundle plus `./supplemental-ui` supplemental files.
- **AsciiDoc extensions** — `asciidoctor-kroki` (diagram rendering) and `@asciidoctor/tabs` (tabbed content blocks).
- **Antora extensions** — `@antora/lunr-extension` configured for bilingual (`en, el`) search with `index_latest_only: true`.

The most consequential part of the playbook for authors is the shared AsciiDoc attribute block. These attributes are inherited by every page and are the canonical place for Greek UI captions and integration endpoints:

```yaml
asciidoc:
  attributes:
    page-toctitle: 'Περιεχόμενα'
    note-caption: 'ΣΗΜΕΙΩΣΗ'
    tip-caption: 'ΣΥΜΒΟΥΛΗ'
    important-caption: 'ΣΗΜΑΝΤΙΚΟ'
    caution-caption: 'ΠΡΟΣΟΧΗ'
    warning-caption: 'ΠΡΟΕΙΔΟΠΟΙΗΣΗ'
    sonarqube-appId: 'CarRental_car-rental_be95db4a-452c-44cf-8ca7-85884c65329f'
    kroki-server-url: https://kroki.nmlabs.gr
```

**Greek UI captions are set here, not per-page.** The admonition captions (`note`, `tip`, `important`, `caution`, `warning`) and the page table-of-contents title (`Περιεχόμενα`) are localized once at the playbook level. This is the only accepted localization mechanism for UI chrome; technical code/API terms stay English by convention. Per the project style guide, user-facing prose is written in Greek, while technical identifiers (API, endpoint, filenames) remain English.

## Component descriptor attributes

`docs/antora.yml` contributes a second layer of AsciiDoc attributes that apply to all pages in the component:

```yaml
asciidoc:
  attributes:
    table-caption: false
    table-stripes: hover
    kroki-fetch-diagram: true
    app-name: nmecar
    app-back: BackOffice
    app-front: Site
```

The `{app-name}`, `{app-back}`, and `{app-front}` attributes let authors refer to product names consistently without hard-coding strings. `kroki-fetch-diagram: true` (combined with `kroki-server-url` from the playbook) enables Antora to fetch and embed Kroki-rendered diagrams at build time, so the generated HTML does not depend on the Kroki server at view time. See [Kroki & Diagrams](../integrations/kroki-and-diagrams.md) for the diagram authoring workflow.

## Navigation assembly

Navigation is the single most maintenance-sensitive part of the site. It is intentionally *delegated* through a chain of partials so that each content section owns its own nav fragment.

`docs/modules/ROOT/nav.adoc` is the top-level entry point. It declares the home page link and then delegates the rest of the tree to one partial:

```asciidoc
* xref:index.adoc[]

include::partial$nav_main.adoc[]
```

`partials/nav_main.adoc` is the section index. For each major section it declares the section landing page (`xref:<section>/index.adoc[]`) and immediately includes that section's nav partial:

```asciidoc
* xref:fleet/index.adoc[]
include::partial$nav_fleet.adoc[]

* xref:booking/index.adoc[]
include::partial$nav_booking.adoc[]

* xref:admin/index.adoc[]
include::partial$nav_admin.adoc[]
...
```

Each section partial (`nav_booking.adoc`, `nav_admin.adoc`, `nav_fleet.adoc`, `nav_reporting.adoc`, `nav_technical.adoc`, `nav_release_notes.adoc`) contains the `** xref:` leaf entries for the pages in that section. The technical partial also demonstrates a third-level entry (`*** xref:technical/rest-api-endpoints.adoc[]` nested under the REST API page).

### Updating navigation

When a page is added, removed, or renamed, the contributor's contract is: **always update `nav.adoc` *and* the relevant `nav_*.adoc` section partial together.** Because `nav.adoc` only delegates to `nav_main.adoc`, the practical rule is to keep the section landing entry in `nav_main.adoc` and the leaf entries in the matching `nav_<section>.adoc`. Skipping either produces a navigation tree that points to a missing page or omits a page that exists, and the build emits `xref` warnings.

## Reusable partials

Beyond navigation, the partials directory holds fragments designed to be included rather than duplicated. Authors should prefer `include::partial$...[]` over copying markup.

- **`caution.adoc`** — a single CAUTION admonition noting that `{app-name}` is under development. Including it reuses the wording and the attribute substitution automatically.
- **`sonarqube.adoc`** — renders a full row of SonarQube quality badges by repeatedly setting `:sqb-metric:` / `:sqb-metric-caption:` and including the badge partial.
- **`sonarqube_badge.adoc`** — a single parametrized badge that builds an image URL from `{sonarqube-appId}` (playbook) and `{sqb-metric}` / `{sqb-metric-caption}` (set by the caller).

The badge partial is the key parametrization pattern:

```asciidoc
image:https://sonarqube.nmlabs.gr/api/project_badges/measure?project={sonarqube-appId}&metric={sqb-metric}[{sqb-metric-caption},link=https://sonarqube.nmlabs.gr/dashboard?id={sonarqube-appId}]
```

`sonarqube.adoc` drives it by redefining `:sqb-metric:` before each include, so the same badge template produces distinct metrics (bugs, ncloc, security_rating, etc.). The `:sqb-metric:` attribute must remain intact when editing these partials; the review checklist explicitly verifies that badge partials stay parametrized rather than being hard-coded.

## Content conventions

### Cross-references

Use `xref:` with stable Antora IDs for cross-page links. Never hard-code URLs to internal pages. Stable `[[anchor]]` IDs on headings keep references from breaking when titles change. Pages within the same component are referenced as `xref:<path>.adoc[]` (the `.adoc` suffix is resolved by Antora to the generated URL).

### Filenames and encoding

- Filenames are **kebab-case**, ASCII-compatible, with the `.adoc` extension (e.g., `driver-age-charges.adoc`, `rest-api-endpoints.adoc`).
- All content files use **UTF-8** encoding.

### Diagrams

Text-based diagrams (PlantUML, Mermaid, Graphviz, BPMN, C4) are stored under `docs/modules/ROOT/pages/**` or `specs/diagrams/` and rendered via Kroki directives; with `kroki-fetch-diagram: true` the rendered images are fetched at build time. Static images go in `docs/modules/ROOT/images/` and are referenced with image macros, with alt text and captions for legibility.

## Versioning policy

Documentation versions are treated as **feature-level releases** — `1.0`, `1.1`, `2.0` — not patch-level releases (`1.1.0`), unless patch-specific documentation is explicitly requested. The current component descriptor declares version **`2.0`** (`docs/antora.yml`), and the release-notes section already carries entries for both `2.0` and `1.1` as browsable feature releases.

The versioning policy has several invariants contributors must honor:

- **Preserve previous release state.** When introducing a new versioned documentation set, the previously released documentation state is kept intact so users browsing a deployed feature release can still find matching docs. Antora's multi-version support is the mechanism for released versions.
- **Keep the active line explicitly versioned.** The working documentation line must carry an explicit `version` in `docs/antora.yml`; the component version is never left unset once version-oriented documentation has started.
- **Update both summaries and feature pages per release.** For each feature release, add a release-oriented page (release notes / "what changed") *and* update the affected functional pages — not only the release summary.
- **Release notes are versioned pages.** The `release-notes/` section holds one page per feature release (`2.0.adoc`, `1.1.adoc`), surfaced in the nav via `nav_release_notes.adoc`.

## Build and verification

A merge-ready change is expected to build cleanly with `npx antora --fetch antora-playbook.yml` and produce no unresolved `include` or `xref` warnings. The review checklist additionally requires that navigation entries point to existing pages, breadcrumbs and sidebar render correctly, Sonar badges remain parametrized, and code samples live under `modules/ROOT/examples` with language annotations. The end-to-end build flow — including the theme compilation step and local preview — is documented in [Build & Preview](../operations/build-and-preview.md), and the full CI/CD publish path in [Docs Build Flow](../workflows/docs-build-flow.md).
